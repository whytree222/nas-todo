# NAS 个人功能服务升级

子任务、标签、重复规则和习惯打卡需要本版 NAS 服务。基础待办接口保持兼容；新客户端连接旧 NAS 时，基础任务继续同步，个人信息留在本机队列，不会丢弃。番茄钟不在本版范围内。

## 当前 DX4600 运行项目

1. 在两台设备上同步已有待办。若已经在新版新增个人信息而旧 NAS 不支持，保留本机应用和待上传队列，升级后再上传；不要卸载或清除应用数据。
   有个人数据尚未上传的设备也不要降回旧版应用，旧版无法保留新版个人队列。
2. 在 NAS Docker 界面**停止原项目**，复制整份原 `data` 目录作为升级前备份。复制时保留 SQLite 文件及旁边可能存在的 WAL/SHM 文件。完成后原 `data` 仍留在原位置。
3. 使用本聊天提供的**私有 v0.10.0 运行配置**，只替换原 NAS 项目目录中的 `compose.yaml`，在原项目中重新导入并部署。它沿用原端口、访问令牌、用户和 `./data:/data`，只替换服务器程序。不要把它作为新目录、新数据卷或新项目启动。
4. 不需要重新运行 `todo-init`。检查 `todo-sync` 持续运行，原 `/health` 返回 `{"status":"ok"}`。
5. 两端打开新版应用并同步。“设置 → 个人功能同步”显示“个人功能服务已连接”后，再验证标签、子任务和习惯打卡能在另一端出现。

私有运行配置包含访问令牌，只用于自己的 NAS，**不要上传到 GitHub 或转发**。GitHub Release 中的 NAS 源码 ZIP 不含令牌，也不是这个私有配置。

## 使用源码构建的 Compose 项目

从 Release 下载 `nas-todo-server-v0.10.0.zip`，将其中的 `server/app.py`、`server/Dockerfile` 更新到原源码项目的 `server` 目录。保留原 `.env`、数据目录、挂载和端口，在原项目重建并启动 `todo-sync`。不要执行删除数据卷的操作。

若运行配置把程序嵌入 `compose.yaml`，只替换磁盘上的 `app.py` 不会更新正在使用的程序；应使用上一节的私有运行配置。服务升级和两端应用升级可以分开进行，旧客户端仍可读写基础任务。

## 数据与规则

- 在同一个 SQLite 数据库里事务性增加个人记录、操作去重和重复任务记录表；原待办表、任务 ID、数据库身份、令牌和成就历史不重建。
- 子任务最多五层，禁止循环。删除父任务或月底清理父任务时，保留下来的子任务提升为顶层；不自动完成或删除全部子任务。
- 重复待办完成并同步后，由 NAS 根据该次的安排日期生成下一次，重试、撤销或再次完成不会生成重复实例。新客户端在规则修改完成前会暂缓生成，断网或重启后继续处理；不会按旧规则多生成一项。
- 习惯支持勾选或次数目标、每周计划日、撤销和历史补记。不同设备同时修改同一天的记录时保留冲突，选择本机或 NAS 版本后再同步。
- 成就月底清理范围沿用已确认规则：已结束月份中有日期、有分类的全部待办（含未完成）先归档再清理；无日期、收件箱、未分类保留。习惯和打卡历史不参加待办清理。
- 服务器原有 SQLite 在线备份同时覆盖个人信息、重复记录、习惯、成就和归档。需要恢复时先保留当前数据副本，再停止服务操作；不要混用不同时间的主库和 WAL 文件。

升级后可先用一条测试任务和一个测试习惯验证：离线编辑、联网同步、另一端查看、打卡撤销和应用重启。重复规则的下一次以安排日期为基准；修改已生成的后续安排时直接编辑下一条任务。
